## 3. Findings

### Medium

**[M-1] Malformed JSON request body → 500 instead of 400 (17 routes)** — FIXED
(`fix(api): return 400 (not 500) on malformed JSON request bodies`, commit b21a094)

- **Description:** Every POST/PATCH handler under `api/v1/*` and
  `auth/register` parsed the body with an unguarded `const body = await
  req.json()` inside the route's outer `try/catch`. `req.json()` throws on an
  empty or non-JSON body, so the throw was caught by the generic handler and
  returned `500 Internal server error` — before the handler's own field
  validation (which returns a clean `400`) ever ran.
- **Impact:** A client sending `{}`, no body, or truncated JSON received a
  `500` (a server-fault signal, noisy in monitoring) for what is a
  client-input error. Low security impact; a correctness/robustness issue.
- **Fix:** Wrapped all 17 sites as `await req.json().catch(() => ({}))` — the
  exact pattern already used in `admin/create-test-users` and the DELETE
  handler of `admin/users/[id]`. On a bad body the handler now receives `{}`,
  existing validation runs, and the caller gets the correct `400`. No change
  for well-formed requests. Typecheck + lint clean.
- **Not in public CHANGELOG / no version bump:** invisible to normal users
  (only malformed API calls are affected); the public changelog is
  user-facing only. Documented in `docs/DEVLOG.md` under `[Unreleased]`.

### Low / Nice-to-have (not fixed — backlogged)

**[L-1] Dual lockfiles: `bun.lock` + `package-lock.json` both committed.**
Two package managers' lockfiles in one repo drift independently and can
produce false-positive audit alerts / different dependency trees on different
machines (Common Pitfall #1). Recommend the team pick one authoritative
package manager and delete the other lockfile. Not auto-fixed — deleting a
lockfile is a team/tooling decision, not a "safe" code fix.

**[L-2] `seed` and `cleanup-demo` create `new PrismaClient()` directly** rather
than the shared lazy singleton in `src/lib/db.ts`. Acceptable for one-off
admin/ops endpoints (they `$disconnect()` in `finally`), but it bypasses the
serverless pool params the rest of the app relies on. Low priority; noted for
awareness.

**[L-3] No test suite, no CI.** Already documented as a deliberate v1
limitation in ARCHITECTURE.md §4. Recommended stack (per README): Vitest +
Playwright. Backlogged, not a regression.
