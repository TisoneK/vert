## Executive Summary

Vert is a genuinely well-built, mature app (33 sessions, 24 prior ADRs): restrained design,
a polished YouTube-style watch page, real content, working deep-link URLs, dark mode, solid
server-side input validation, and finished edge pages (404, changelog, contact UI). The
craft is real.

The gap is strategic, not cosmetic: **Vert is built as an all-client-rendered SPA that does
not tell the outside world what's on it.** The two things a video platform lives or dies on —
being **shareable** (rich social previews) and **discoverable** (crawlable, keyboard-navigable
links) — are effectively switched off. That's the throughline behind the two highest-impact
findings. Everything else is polish or hardening.

No Critical findings. 2 High, 4 Medium, 12 Low/polish. Baseline health not re-run (no code
changes; last verified Session 32: tsc 0, eslint 0, `next build` passing).

## Findings (by severity)

### HIGH

**H1 — Watch/channel/category pages ship no per-item share or SEO metadata.**
Every deep route is a thin `'use client'` file rendering `<VertApp/>`
(`src/app/watch/[id]/page.tsx`, `channel/[id]`, `category/[slug]`, `tag/[slug]`, …). The only
`Metadata` in the app is the global one in `src/app/layout.tsx` — there is **no
`generateMetadata` anywhere**. Verified against production: a `/watch/<id>` server response
has `<title>Vert</title>`, the generic site description, **no `og:image`, no `og:video`**,
`twitter:card=summary`, and the video's title ("Floor") does **not** appear in the server HTML
at all. Impact: pasting any Vert link into iMessage/WhatsApp/Slack/X yields a bare "Vert"
card with no thumbnail, title, or inline player; search engines index nothing. This directly
undercuts the product's own tagline ("Watch and **share** portrait video"). The watch page's
own code comment acknowledges it: *"A future SSR pass could populate OpenGraph metadata here."*
No `app/sitemap.ts`/`app/robots.ts` either (only a static `public/robots.txt` that ironically
invites Googlebot/Twitterbot/facebookexternalhit to pages with no server content).
→ **Recommendation:** ADR-25.

**H2 — The Contact form fakes a successful send.**
`src/components/vert/ContactPage.tsx` `handleSubmit` does `await new Promise(r => setTimeout(r, 800))`
then shows *"Message sent — Thanks for reaching out. We'll get back to you by email."* Nothing
is sent anywhere (`// TODO: wire to a real endpoint … For now the form just simulates
submission`). A user who reports a bug or asks a question is told, falsely, that it was
delivered. This is a trust/integrity issue, worse than an obviously-unfinished placeholder.
→ **Recommendation:** ADR-27.

### MEDIUM

**M1 — Content navigation uses `<div onClick>`, not real links; zero `<a>` anchors on content pages.**
`VideoCard`'s root is `<div className="group cursor-pointer" onClick={() => navigate(...)}>`
(`VideoCard.tsx:100-117`) — no `href`, no `role`, no `tabIndex`. The homepage has **0 `<a>`
tags**. Navigation works (zustand + `history.pushState` in `store.ts`), so URLs are shareable,
but: not crawlable (crawlers don't run onClick), not keyboard-focusable/activatable, and no
middle-click / ⌘-click / "open in new tab" / "copy link". It also nests real `<button>`s
(channel name, tags, context menu) **inside** the click-navigable div — an interactive-nesting
a11y anti-pattern. (Only `not-found.tsx` and `error.tsx` use real anchors — the inverse of
where you'd want them.) → **Recommendation:** ADR-26.

**M2 — Rate limiting is per-instance in-memory; ineffective on serverless.**
`src/lib/rate-limit.ts` is a module-level `Map`. Its own comment says *"v1 architecture is
single-instance … sufficient"* — but the app runs on **Vercel serverless**, which is
multi-instance and recycles/cold-starts lambdas. So `login` (10/min/IP) and `signup`
(5/min/IP) counters are per-instance and reset frequently; an attacker's requests spread
across instances, making brute-force / account-spam protection much weaker than it reads.
→ **Recommendation:** ADR-28 (move the store to Vercel KV / Upstash behind the same interface).

**M3 — No password-reset / "Forgot password?" flow.**
`LoginForm` has no reset link, and there is no reset route (only authenticated
`/api/v1/auth/change-password`). Email/password users who forget their password are permanently
locked out. The register route's own comment references "password-reset flows" that don't
exist. Needs an email provider (already flagged in prior sessions as a user-action blocker).

**M4 — Weak password policy (min 6, no strength/breach check).**
`SignupForm.tsx:34` and `register/route.ts:66` both enforce only `length >= 6`. 8+ is the
modern baseline; consider a breach/common-password check. (Server validation is otherwise
strong — see Positives.)

### LOW / POLISH (mostly the "visible mistakes")

- **L1 — 404 and 500 pages are hard-coded light mode.** `not-found.tsx` and `error.tsx` use
  `bg-white` / `text-zinc-900` with **no `dark:` variants** → a white flash/page in dark mode.
  → ADR-29.
- **L2 — Trending #1 hero wastes horizontal space.** The featured portrait thumbnail sits
  centered in a very wide gray container, leaving large empty areas left and right on desktop.
- **L3 — Trending category chips clip "Travel"** ("Trav") at the right edge of the scroller.
- **L4 — Empty categories presented as equal options.** Explore/Trending list Art, Comedy,
  Food, Music, News, Other, Travel as filters that resolve to "No videos yet" — dead ends.
  Consider hiding/greying empty categories until they have content.
- **L5 — Search matches titles only.** Query "music" → "No videos found" despite a `music`
  tag and a Music category existing. Search should also index tags/categories/channel names.
- **L6 — Thumbnails flash empty gray on first paint.** No blur-up/`placeholder="blur"` on the
  `next/image` thumbnails, so image-heavy feeds show gray boxes briefly before paint.
- **L7 — `twitter:card=summary`** (small square) rather than `summary_large_image` — cramped
  previews even once OG images exist (folds into ADR-25).
- **L8 — Header inconsistency across the `/` boundary.** The logged-out landing header has no
  search bar; the in-app header does — reads like two different apps.
- **L9 — Crowded mobile header.** At 375px the header carries hamburger + logo + search +
  theme toggle + "Log In" + "Sign Up" — tight; one auth CTA up top would breathe.
- **L10 — "ADVERTISEMENT — Reserved placement" shows on public watch pages.** Provider-neutral
  by design (ADR-15/22) but still reads as unfinished to a first-time visitor.
- **L11 — ~97 `console.*` calls in `src/`** — production log noise; audit for any that echo
  request/DB detail.
- **L12 — Upload token-gen failure returns raw `details: errorMsg`** (`upload/route.ts:105`) —
  minor internal-detail leak; low risk (authenticated), but prefer a generic message + server log.
- **L13 — No Content-Security-Policy header** (X-Frame-Options + HSTS are set). Add a CSP.

## What's genuinely good (verified, keep)

- **Server-side auth validation is strong.** `register/route.ts`: IP rate-limited, non-string
  password guard (400 not 500), email regex + length cap, username rules, **bcrypt cost 12**,
  case-insensitive duplicate check.
- **Sensitive endpoints are gated.** `debug-db` is admin-only (returns 403 otherwise);
  ops endpoints (`seed`/`cleanup-demo`) are env-gated (Session 5). Upload requires auth +
  rate limit + content-type allowlist + 200MB cap + direct-to-blob client token.
- **Player accessibility.** All controls `aria-label`led; settings popup keyboard-safe (ADR-14);
  responsive volume disclosure (ADR-24).
- **Perf work already landed:** `next/image` AVIF/WebP (ADR-5/12), lazy loading (ADR-4),
  hover/touch react-query prefetch (ADR-3).
- **Deep-linkable URLs** via `pushState` + `popstate`; **dark mode** with a no-flash inline
  script in `layout.tsx`.
- **Well-built secondary surfaces:** search (format filters, Videos/Channels tabs, clean empty
  state), explore (category counts), channel page, changelog (version sidebar), 404 content.
